# 压测与故障注入记录

本目录包含一个**纯 JDK 实现的压测客户端**（`Bench.java`，无第三方依赖），以及用它测出来的结果。

所有数字都是在本机真实跑出来的，可以用下面的方法复现；**没法复现的指标一律不写**。

## 一、压测环境

| 项 | 值 |
| --- | --- |
| 机器 | Windows 11 + AMD Ryzen 9 7945HX，16GB 内存 |
| 被测服务 | 本机启动的 Spring Boot（JDK 17 / Spring Boot 3.2.5），端口 18080 |
| 中间件 | 同机 Docker：MySQL 8.0（13306）、Redis 7.2（6379）、RocketMQ 5.1.4（9876）、MinIO（9000） |
| 压测客户端 | 与中间件、服务**同机**（所以数字反映的是"这台机器上的相对变化"，不是生产环境的绝对能力） |
| 压测方式 | 闭环压测：N 个虚拟线程，每个线程串行发 `总请求数 / N` 次，统计 P50 / P90 / P95 / P99 |

运行方式：

    java Bench.java --base http://localhost:18080 --tokens bench/tokens.txt --path /api/bench/apply-async/1 --concurrency 50 --requests 2000

## 二、异步化前后的对比（同一接口、同一台机器）

对照组：`/api/bench/apply-sync/{jobId}`（同步版，接口内直接解析简历 + 匹配打分 + 通知）
实验组：`/api/bench/apply-async/{jobId}`（异步版，接口只做校验、落库、发 MQ）

两个接口都**刻意剥离了限流、幂等键与分布式锁**，用来隔离「要不要等外部调用」这一个变量——所以下表是**受控对照实验**的绝对值，不等于线上投递接口的端到端耗时。

> **本表数字的口径**：下表取自**数据卷复测轮**（MySQL / Redis / RocketMQ 的数据目录放在 Docker 数据卷上，而不是挂载 Windows 本机目录）。本机保留的原始记录里另有一轮「挂载目录」的数据（同步 849 ms / 异步 20 ms、50 并发吞吐 51 / 209 req/s），与本表的 841 ms / 21 ms、50 / 275 req/s 是**两轮不同环境**各自的采集结果，不是同一批数字的两种写法。

| 指标 | 同步版 | 异步版 |
| --- | --- | --- |
| 单请求响应时间 | 841 ms | **21 ms** |
| 50 并发吞吐 | 50 req/s | **275 req/s**（复测 289 req/s，该次采集的原始输出未入库） |
| P50 | 880 ms | **93 ms** |
| P95 | 1269 ms | **583 ms** |
| P99 | 1284 ms | **596 ms** |

**结论**：把简历解析、匹配打分、通知推送移出请求线程，接口不再等待任何外部调用，单请求耗时下降了约 40 倍，50 并发下吞吐提升约 5.5 倍。

**压力的去处**：并发从 50 提到 500 后，吞吐落在 366~503 req/s、P99 涨到 1.76~2.22 s，说明瓶颈已经从"外部调用"转移到了服务端线程与本机资源（数据库连接池上限 20、压测客户端与服务同机争抢 CPU）。**这组数据不作为结论使用**，它的价值是说明"并发不是越高越好"。

## 三、内容级去重与秒传

| 实验 | 方法 | 结果 |
| --- | --- | --- |
| 重复投递拦截 | 同一账号对同一岗位间隔 1.2 秒连续提交 6 次 | 数据库最终只有 **1 条**投递记录：1 次成功、4 次"请勿重复提交"、1 次"你已经投递过该职位" → 拦截率 100% |
| 内容级秒传 | 同一份文件重复上传 10 次 | 秒传命中 **9/10**（第 1 次上传必然走完整链路，从第 2 次起才命中），`resume_file` 始终只有 1 行 → **只触发 1 次解析**（重复解析下降 90%） |
| 跨用户秒传 | 用户 A 上传后，用户 B 上传同一份文件 | B 命中秒传，但拿到的是**自己的** fileId，两条记录指向同一个存储对象 |

**没有采用的口径**：不写"节省了 X% 的 Token"。因为解析链路用的是可注入故障的 Mock 实现，Token 数只能靠假设，无法验证——所以只写"同一文件重复上传 10 次只触发 1 次解析"这种能被复现的说法。

## 四、断点续传

| 步骤 | 结果 |
| --- | --- |
| 25MB 文件切成 5 片（5MB/片） | — |
| 传完第 1~3 片后中断 | — |
| 重新调用 init | 返回 `uploadedParts=[1,2,3]` |
| 前端只补传第 4、5 片 | **重传量 = 未完成的部分（2/5）**，合并后文件大小与源文件一致 |

**没有采用的口径**：不写"重传数据量下降 60%"。省下多少取决于断在第几片（传完 3 片才断就省 3/5，传完 1 片就断只省 1/5），这个百分比没有信息量。只写绝对量和规律：**重传量 = 未完成的分片数，断得越晚要补的越少**。

## 五、指数退避重试 + 幂等 + 死信

通过 `offermate.mock.parser-fail-rate` 注入三方解析故障（每次调用按概率抛"connection reset"），跑 200 次对比：

| 注入的失败率 | 单次调用成功率 | 重试后的最终成功率 |
| --- | --- | --- |
| 30% | 68.0%（136/200） | **99.50%**（199/200） |
| 50% | 48.5%（97/200） | **93.00%**（186/200） |

理论值也对得上：最多**尝试** 4 次（1 次原始 + 3 次重试，`offermate.retry.max-attempts=4`），30% 失败率下四次全失败的概率是 0.3⁴ ≈ 0.81%，即理论成功率约 99.2%，实测 99.5%。

**边界**：故障率提到 50% 时最终成功率掉到 93%，而且每次重试都在占用线程与时间——所以重试必须配"退避 + 次数上限 + 死信兜底"，超限的消息进 `%DLQ%cg_resume_parse`，由后台按业务 ID 重放。

## 六、令牌桶限流

| 场景 | 配置 | 结果 |
| --- | --- | --- |
| 投递接口并发 10 次 | 容量 5、每秒补 1 | **5 次通过 + 5 次 429**（与桶容量完全一致） |
| AI 对话并发 20 次 | 容量 10、每秒补 2 | **13 次通过 + 7 次 429**（桶内 10 个令牌 + 请求过程中补充的令牌） |
| 正常节奏（每 1.2 秒 1 次） | 同上 | **全部通过**（正常用户不受影响） |

## 七、traceId 链路验证

同一次请求的日志中，HTTP 入口、MQ 生产、MQ 消费三条日志的 traceId 完全一致（例如 `[TESTTRACE123]`），说明 traceId 已随消息属性跨进程传递，线上排查时可以用一个 ID 串起全链路。

## 八、复现要点

1. 需要 `bench` Profile 启动被测服务，才会注册压测专用接口：`--spring.profiles.active=bench`
2. 令牌文件 `bench/tokens.txt` 是本机压测时生成的登录令牌，**不入库**，需要自己登录后重新生成
3. 故障注入改的是配置项，不需要改代码：`offermate.mock.parser-fail-rate=0.3`
