# 压测结果记录（真实跑出来的数字）

> 这次压测是**在这台机器上真跑出来的**，不是估的。环境、方法、数字都在这里，面试被追问时照实说即可。

## 一、环境

| 项 | 值 |
| --- | --- |
| 机器 | 本机 Windows，AMD Ryzen 9 7945HX / 16GB |
| 中间件 | Docker Desktop 起的 MySQL（13306）、Redis（6379）、RocketMQ（9876） |
| 服务 | 同一个 Spring Boot 应用（Tomcat，端口 18080） |
| 压测客户端 | 自研 JDK 压测工具（bench/Bench.java），**与服务跑在同一台机器上** |
| 外部依赖 | 三方解析用 Mock 模拟，单次耗时 800ms（application.yml 里的 offermate.mock.parser-latency-millis） |

## 二、方法（为什么这样比是公平的）

- 压测专用接口两个，只在 bench 配置下注册，**生产不暴露**：
  - /api/bench/apply-sync：落库 → 等三方解析（800ms）→ 等写站内信 → 返回（重构前的写法）
  - /api/bench/apply-async：落库 → 发两条 MQ → 立刻返回（现在的写法）
- 两个接口的差异**只有一处**：要不要等外部调用。其余完全一致（为隔离这一个变量，两个 bench 接口都刻意不做限流、幂等键与分布式锁）。
- 每轮压测前先清空 application / notification 表，避免唯一约束冲突造成的失败混进延迟统计。
- 只采用 **100% 成功**的那一轮数据（成功率 100% 才算有效样本）。
- 闭模型压测：固定 N 个并发用户，每个用户串行循环发请求，所以延迟是真实的单请求耗时。

## 三、结果

### 1) 单请求对比（最能说明问题）

| 版本 | 单次请求耗时 |
| --- | --- |
| 同步版（等外部调用） | **849 ms** |
| 异步版（发消息就返回） | **20 ms** |

### 2) 50 并发压测（各 200~300 次请求，成功率 100%）

| 指标 | 同步版 | 异步版 | 提升 |
| --- | --- | --- | --- |
| 吞吐 | 51 req/s | **209 req/s** | **约 4 倍** |
| P50 | 870 ms | **159 ms** | 5.5 倍 |
| P95 | 1241 ms | **534 ms** | 2.3 倍 |
| P99 | 1299 ms | **553 ms** | 2.3 倍 |
| 平均 | 946 ms | **214 ms** | 4.4 倍 |

### 3) 高并发下的现象（可以作为"我知道系统边界"的素材）

- 异步版在 **500 并发**下 P50 升到 286ms、P99 升到 1.76s，吞吐停在 503 req/s——**服务端饱和了**（Tomcat 工作线程 200 个，超出的请求在排队）。
- 这说明：**并发数不是越高越好**，瓶颈从"外部调用"变成了"服务端线程数 + 本机 IO"。

## 四、简历上可以怎么写（照抄，把数字保持真实）

**推荐版（两行，已压到最短）**：

> 引入 RocketMQ 将简历解析、JD 匹配与通知推送全链路异步化，投递主链路只保留校验、落库与消息投递；
> 接口单次响应 841ms → 21ms（受控对照接口，剥离限流/幂等/分布式锁），50 并发下吞吐提升约 5.5 倍（50 → 275 req/s），P99 1.28s → 596ms（本机 Docker 实测）

**极简版（只留最硬的数字）**：

> 将简历解析、匹配、通知改为 MQ 异步处理，投递链路不再等待外部调用：接口单次响应 841ms → 21ms（受控对照接口），50 并发吞吐 50 → 275 req/s（本机 Docker 实测）

## 五、被追问时的标准答法

> "同一套代码我写了两个分支做对比：一个把解析、算分、通知同步做完才返回，另一个只落库加发消息。用自己写的压测工具打 50 并发，每轮压测前清空数据表，只取成功率 100% 的那轮。
> 数字上单请求是 849ms 对 20ms，50 并发下吞吐 51 对 209。**我要说明两个边界**：一是中间件是我本机 Docker 起的，客户端和服务在同一台机器上，绝对值不代表线上；二是我还压到过 500 并发，那时候服务端线程打满、P99 反而涨到 1.7s，所以我不会说'并发越高越好'。"

## 六、复现命令

    cd offermate/bench
    java -Dstdout.encoding=UTF-8 Bench.java --prepare 200 --base http://localhost:18080
    java -Dstdout.encoding=UTF-8 Bench.java --path /api/bench/apply-sync  --concurrency 50 --requests 200 --jobs 200 --base http://localhost:18080
    java -Dstdout.encoding=UTF-8 Bench.java --path /api/bench/apply-async --concurrency 50 --requests 300 --jobs 200 --base http://localhost:18080

> 小提示：--prepare 造账号时会撞上登录接口「按 IP 每秒 5 次」的限流，所以账号数不要贪多，
> 用 --jobs 参数保证「用户 + 岗位」组合不重复即可（例如 35 个账号配 --jobs 200）。

# 八、去重 / 秒传 / 断点续传 实测（用真实接口跑的，不是估算）

## 1) 重复投递拦截率 = 100%

同一用户对同一岗位**连续提交 6 次**（每次间隔 1.2 秒，避开令牌桶限流）：

| 第几次 | 结果 | 被谁拦下的 |
| --- | --- | --- |
| 第 1 次 | 投递成功（applicationId=201） | — |
| 第 2、3、4、6 次 | 请勿重复提交 | **Redis 幂等键**（5 秒窗口内） |
| 第 5 次 | 你已经投递过该职位 | **业务判重**（查投递表） |

数据库最终记录数：**1 条** → 拦截率 **100%**。
附带价值：这组实验证明**两层拦截各自都在生效**（不是只有一层在挡）。

## 2) 内容级去重（防海投）生效

同一用户**换一个岗位、但属于同一家招聘方**再投 → 直接被拦：

> 同一份简历 24 小时内不能重复投递同一招聘方，修改简历后再试

## 3) 秒传命中 + 重复解析下降 90%

同一份文件**重复上传 10 次**：

- 秒传命中 **9 / 10**（第 1 次上传必然走完整链路，从第 2 次起才命中；命中时返回 instantUpload=true，一个字节都不用传）
- 文件表里始终只有 **1 行**记录 → 只解析了 1 次
- 即 **重复解析下降 90%**（9 / 10）

## 4) 断点续传：重传量 = 未完成的分片数（不写百分比）

25MB 文件切成 5 片（每片 5MB），只传前 3 片就停下（等价于用户关掉页面）：

1. 第一次 init → 得到 uploadId
2. 上传第 1~3 片（每片都成功）
3. **重新 init**（等价于刷新页面）→ 服务端返回同一个 uploadId、**uploadedParts=[1,2,3]**
4. 只补传第 4、5 片 → 调合并接口返回成功，数据库状态 DONE、大小正好 5×5MB=**25MB**

结论：**传 5 片、断在第 3 片，续传只补 2 片——重传量 = 未完成的分片数**，断得越晚要补的越少（断在第 4 片就只补 1 片）。

**不采用「重传数据量下降 60%」这个口径**：省下多少完全取决于断在第几片（传完 3 片断是 3/5，传完 1 片断就只有 1/5），同一套系统能报出任何数字，所以只写绝对量和规律（与 bench/压测说明.md 第四节一致）。

## 4.5) 重试机制到底能救回多少？（400 次实测）

用**真实的指数退避重试组件**，注入可控失败率，统计"单次成功率"和"最终成功率"：

| 注入的失败率 | 单次调用成功率 | 加重试后的最终成功率 |
| --- | --- | --- |
| 30% | **68.0%**（136/200） | **99.50%**（199/200，只失败 1 次） |
| 50% | **48.5%**（97/200） | **93.00%**（186/200） |

理论对得上：最多**尝试** 4 次（1 次原始 + 3 次重试，`offermate.retry.max-attempts=4`），30% 失败率下四次全败概率 0.3⁴≈0.81%，即理论成功率约 99.2%（实测 99.5%）。

**边界（面试要主动说）**：故障率提到 50% 时最终成功率掉到 93%，而且每次重试都在占线程和时间——所以重试必须配"退避 + 次数上限 + 死信兜底"，超限的任务交死信人工处理。

简历措辞：
> 应对三方 API 网络抖动使用指数退避重试机制，配合消费幂等表与死信队列兜底失败任务；故障注入 30% 失败率下，单次调用成功率 68%，加入指数退避重试后最终成功率 99.5%（200 次任务实测）

## 5) 有一条我明确不测、也不写进简历

**Token 消耗下降百分比**：项目里的简历解析是 Mock，没有真调大模型，token 数只能靠假设。
所以简历上**不写 Token 百分比**，改写成能验证的说法：**「同一文件重复上传 10 次只触发 1 次解析」**。

# 九、限流实测 + traceId 贯通验证

## 1) 令牌桶限流（打真实接口）

| 实验 | 配置 | 结果 |
| --- | --- | --- |
| AI 对话接口并发 20 次 | 容量 10 / 每秒补 2 | **13 次通过 + 7 次 429** |
| 投递接口并发 10 次（同一用户同一岗位） | 容量 5 / 每秒补 1 | **正好 5 次通过 + 5 次 429** |
| 正常节奏（每 1.2 秒 1 次，连发 4 次） | 同上 | 第 1 次被限（桶刚被掏空），**之后 3 次全部通过** |

**结论**：突发会被削掉、正常用户不受影响；桶是**按速率慢慢补回来**的。

## 2) traceId 贯通 HTTP → MQ → 消费端（新增能力）

请求头带 X-Trace-Id: TESTTRACE123：

- 响应头原样返回 X-Trace-Id: TESTTRACE123
- 应用日志：16:26:58.243 INFO [TESTTRACE123] ResumeParseConsumer - 简历解析成功 fileId=9003
- 下游日志：16:26:58.290 INFO [TESTTRACE123] MockSmsClient - [MockSms] 发送短信 ...

**同一串 ID 从接口一路跟到消费端**，线上排查时按 traceId 搜一次就能拿到整条链路的日志。

简历措辞（第④条可以补上）：
> 基于 Redis + Lua 实现令牌桶限流（投递 5 容量 / 每秒补 1，AI 对话 10 容量 / 每秒补 2）；实测突发 10 次投递只放行 5 次、其余返回 429，按正常节奏请求则全部通过

# 十、存储方式优化后的复测（数据卷 vs 挂载目录）

## 改了什么

把 MySQL / Redis / RocketMQ 的数据从「挂载 Windows 本机目录」改成 **Docker 数据卷**。
原因：Windows 上挂载目录的读写要穿过虚拟机那一层，**磁盘 IO 最慢**；数据卷就在虚拟机内部，省掉这一层。

## 两轮对比（都是 50 并发、100% 成功、测前清空数据表）

| 指标 | 挂载目录（第一轮） | **数据卷（第二轮）** | 变化 |
| --- | --- | --- | --- |
| 异步版吞吐 | 209 req/s | **275 req/s** | **+32%** |
| 异步版 P50 | 159 ms | **93 ms** | **-42%** |
| 异步版 平均 | 214 ms | **165 ms** | -23% |
| 异步版 P99 | 553 ms | 596 ms | 基本持平（尾部受同机压测的 CPU 竞争影响） |
| 同步版吞吐 | 51 req/s | 50 req/s | 不变（它被 800ms 的模拟外部调用主导，IO 影响看不出来） |
| 单请求 同步 / 异步 | 849 / 20 ms | **841 / 21 ms** | 基本不变 |

## 结论怎么讲

- **只有异步链路的"中位数"明显变好**（P50 159→93ms、吞吐 209→275）：因为它的成本正好落在"一次数据库写入 + 两次发消息"上，IO 变快它直接受益；
- **同步链路几乎没变**：它的耗时被 800ms 的模拟外部调用主导，IO 快慢根本看不出来——**这也反过来说明：异步化之后，成本结构真的变了**；
- **P99 尾部没有变好**：因为尾延迟主要来自"压测客户端和服务在同一台机器上抢 CPU"，不是磁盘。

## 500 并发（噪声较大，仅作定性）

| 指标 | 挂载目录 | 数据卷 |
| --- | --- | --- |
| 吞吐 | 503 req/s | 366 req/s |
| P99 | 1.76 s | 2.22 s |

**这一组数字波动大、且比 50 并发明显更差**，原因是：500 并发已经超过 Tomcat 的 200 个工作线程，而且压测客户端和服务跑在同一台机器上互相抢 CPU。
所以它只能说明一件事：**并发不是越高越好，瓶颈会从"外部调用"转移到"服务端线程 + 本机资源"**——这也是我不会在简历上写"500 并发"的原因。
