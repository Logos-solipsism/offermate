## 三、刻意保留的取舍（设计决策记录）

1. 匹配打分用**技能标签重合率**，不做向量召回与推荐模型——重点在于"异步算分链路"而不是算法本身。
2. 没有引入缓存层（Spring Cache / 多级缓存 / 布隆过滤器）：当前数据量级不支撑，加了只有成本没有收益。
3. 没有做分库分表与分布式事务，投递链路的最终一致用"唯一索引 + 幂等表 + 死信重放"解决。
4. AI 侧只读不写：工具方法不产生任何写操作，避免模型误操作业务数据；身份一律取自服务端上下文。
5. 分片合并用 ComposeObject 而非 S3 MultipartUpload（minio-java 公开 API 未提供对应 Args 类）：换来的是只用一套 SDK，代价是峰值 2 倍存储与一次额外 IO，属于明确记录的取舍。
6. 分片上传的前端指纹用 spark-md5 分片增量计算（主线程），超大文件可进一步挪到 Web Worker。

## 四、本地运行与验证

1. `docker compose --profile minio up -d` → 执行 `db/schema.sql`，可选再执行 `db/data.sql` 导入演示数据
2. 启动后端（`mvn spring-boot:run`），启动前端（`cd web && npm install && npm run dev`）
3. 用演示账号 13911110001 / 123456 登录，上传一份简历，观察"解析中 → 解析完成 + 技能标签"
4. 同一份文件再传一次，确认秒传命中（本次上传 0 字节）
5. 投递职位 → 查看"我的投递"里的状态与匹配分 → 查看站内信
6. 用 HR 账号（13811110001 / 123456）改状态为"面试邀约"，再回求职者端看站内信
7. 接口文档：<http://localhost:18080/doc.html>；把 `offermate.mock.parser-fail-rate` 调成 0.3 重启，可观察 mq_consume_log 里的重试记录
