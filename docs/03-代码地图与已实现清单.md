## 三、刻意保留的取舍（设计决策记录）
1. 匹配打分用**技能标签重合率**，不做向量召回与推荐模型——重点在于"异步算分链路"而不是算法。
2. 缓存直接用 Spring Cache + Redis，没有引入多级缓存与布隆过滤器；数据量级不支撑，讲了反而是减分。
3. 没有做分库分表与分布式事务，投递链路的最终一致用"唯一索引 + 幂等 + 补偿"解决。
4. AI 侧只读不写：工具方法不产生任何写操作，避免模型误操作业务数据。
5. 分片合并用 ComposeObject 而非 S3 MultipartUpload（minio-java 公开 API 限制）：换来的是只用一套 SDK，代价是峰值 2 倍存储与一次额外 IO，属于明确记录的取舍。

## 四、本地自测顺序（建议）
1. docker compose up -d → 执行 schema.sql
2. 启动服务，注册两个账号（SEEKER / HR）
3. 用 Knife4j（http://localhost:18080/doc.html）走一遍：init → chunk → merge → 查 resume 解析状态
4. 同一 MD5 再调一次 init，确认秒传命中
5. 投递 → 看 application 表与 notification 表 → 调 /api/ai/chat 问"我的投递进度"
6. 把 offermate.mock.parser-fail-rate 调成 0.3，重启，观察 mq_consume_log 里的重试记录
